# 0.3.0 evidence ledger

This page is the acceptance ledger for the 0.3.0 workbench scope. It separates
implemented code from behavior that has been exercised at the public boundary.
A capability is not marked complete because a type, binding, or handle exists.
The ledger must be updated with a reproducible command, fixture, and observed
result when a row changes.

## Status vocabulary

- **Exercised** — the consumer-visible path was run and its expected result was
  observed. The evidence column identifies the test, fixture, or UI workflow.
- **Partial** — some implementation or lower-level coverage exists, but an
  acceptance boundary, error path, or integration path remains unverified.
- **Missing** — the required behavior is not implemented or no usable evidence
  exists.
- **Blocked** — implementation is present, but an external prerequisite (for
  example unavailable hardware or a provider) prevents the specified scenario.
  A blocked row is not a pass.

The status applies to the requirement, not to the apparent maturity of its
implementation. `cargo check`, a binding smoke test, or a non-empty result is
not evidence for an end-to-end row.

## Required evidence record

For each exercised row, record:

1. the exact command or UI workflow and repository revision;
2. fixture identity, source format, viewport/DPR/device, and relevant options;
3. observed output, including expected failures and diagnostics;
4. test discovery count and process exit status where a test runner is used;
5. external limitations, unsupported capabilities, and raw artifact paths.

A skipped WebGPU backend, unavailable notebook host, provider outage, or
missing redistributable chemistry resource must be recorded as a limitation;
none converts a partial row into an exercised row. Keep implementation notes in
the owning module and keep this page limited to acceptance evidence and status.

## Measured performance against the specification targets

Release build on an Apple M5 Pro, Criterion with warm-up, revision `787a0a7` plus
the selection scans described below. Inputs are the embedded 1AON (58,870 atoms),
4HHB and smaller structures. Linear scaling to 100,000 atoms is stated as
extrapolation, not as a measurement.

| Target | Measured | Verdict |
| --- | --- | --- |
| mmCIF read to a `Structure` above 200 MB/s (program target 300 MiB/s) | `cif_read`: 231 MiB/s 1CRN, 216 MiB/s 1UBQ, 228 MiB/s 4HHB (3.20 ms), from 198–211 MiB/s | Spec target met; the 300 MiB/s program target is not. Top remaining frame: `Lexer::next_token` (about a third of samples), then the projection sink and number parsing |
| BinaryCIF container parse above 1 GB/s | 0.37–4.4 GiB/s (1CRN to 1AON) | Met for the larger inputs |
| BinaryCIF read to a `Structure` above 1 GB/s | `bcif_read/1aon`: 7.53 ms for 2.77 MiB, 369 MiB/s end to end (13.96 ms, 199 MiB/s before); 4HHB 462 MiB/s. Split: `bcif_decode_columns/1aon` 2.40 ms, `bcif_lower/1aon` 5.13 ms (11.29 ms before) | Not met. Top remaining frames: per-row symbol lookups (`symbol_of`), `decode_stage`, `ChunkBuilder::push` |
| `Document` to `Structure` for 100,000 atoms, under 20 ms | `cif_lower/100k`: 58.5 ms on 100,000 tiled 1AON atoms (69.5 ms before) | Not met |
| Time to first atom, 5 MB mmCIF | `cif_first_atom/5mb`: 12.8 µs (bounded-window batch source, first batch) | Met |
| Full facade read (`read_bytes`) of 58,870 atoms | `facade_enrich/1aon` (default perception alone): 10.97 ms, from 31.3 ms; bond perception now runs in parallel cell blocks | Reported |
| Topological selection, 100,000 atoms, under 1 ms | `chain A` 0.014 ms, `bfactor > 20` 0.31 ms on 58,870 atoms; `query_prune/element_zn_100k`: 105 ns with chunk-statistics pruning (0.97 ms before) | Met |
| SASA, 100,000 atoms, 960 points, under 2 s | `shrake_rupley_100k_960`: 122 ms on 100,000 atoms (232.5 ms before), one streaming engine with lane-parallel occlusion | Met |
| Radius query, 100,000 atoms, 5 Å, under 100 µs | `spatial_cell_list/radius_100k_5A`: 294 ns against a prebuilt index | Met |
| Cell-list build, 100,000 atoms, under 5 ms | `spatial_cell_list/build_100k`: 1.37 ms (eager `CellList::build_in`) | Met |
| RMSD, 10,000 atoms | `geom_coordinates/rmsd_10k`: 6.68 µs (1.50 Gelem/s) | Reported |
| Coordinate hand-off to NumPy without a copy | `facade_handoff/positions_slice`: 0.83 ns; the slice pointer is asserted equal across calls | Met |
| Python import under 50 ms | 1.2 ms median over five subprocess imports of a release abi3 build; `python/tests/test_import_time.py` asserts the 50 ms budget | Met |

Column predicates used to cost one hierarchy walk and a binary search per atom.
Residue- and chain-level predicates now decide once per residue and return runs,
and the thresholded `bfactor` and `occupancy` columns read each chunk directly.
On 58,870 atoms `chain A` fell from 1.05 ms to 0.014 ms and `bfactor > 20` from
0.72 ms to 0.31 ms; on 4HHB the typed and textual selection benchmarks fell from
44 µs and 93 µs to 17 µs. `bfactor > 20` keeps most atoms, so the rest of its
cost is building the selection rather than comparing values.

### Superposition and streamed block results

Same machine and method. QCP (`3cd4e9c`) was measured against the revision
before it (`3cd4e9c^`) and against its own rotation-free form on the 10,000-atom
fixture; the block-streaming changes were measured against the revision before
each.

| Change | Benchmark | Before | After |
| --- | --- | --- | --- |
| QCP superposition | `geom_coordinates/superpose` (small sample) | 18.515 µs | 18.245 µs |
| QCP superposition | `geom_coordinates/rmsd`, `rmsd_10k` | 3.206 µs, 6.698 µs | 3.198 µs, 6.717 µs |
| QCP, rotation built vs not | `superpose_10k` vs `rmsd_after_fit_10k` | — | 38.0 µs vs 37.9 µs |
| Stream accessible-area blocks | `surface_geometry/lee_richards`, `surface_extended/surface_points` | 31.79 ms, 377.6 µs | 31.56 ms, 365.6 µs |
| Stream cell-list pair blocks | `spatial_pairs_within/CellList`, `spatial_scaling/cell_list/1aon` | 625.5 µs, 8.999 ms | 590.9 µs, 8.745 ms |
| Stream bond-perception blocks | `facade_enrich/1aon` | 13.58 ms | 13.51–13.61 ms |
| Stream contact-potential blocks | `analysis_potential/contact_potential_64_cubed` | 9.4 ms | 7.9–11.9 ms (noise) |

QCP is performance-neutral: both fits are dominated by the single O(n)
covariance pass, so the 4×4 eigenproblem it replaces is not on the critical
path at these sizes. It is kept for its specified behaviour (a rotation-free
minimum deviation for streams, a Jacobi fallback on repeated roots), not as a
speed-up. The streaming changes are memory-bound: the peak is the result plus
a bounded block window rather than the result twice, and the bond and
contact-potential paths are equal within noise. The accumulator reductions in
`molframe-spatial` and the frame-block merge in `molframe-traj` keep
`map_blocks_in`: their contracts hand the caller one partial per block to merge
in one step, so there is no per-block output to stream without changing them.

## Experimental research pilot (2026-10-04)

This exploratory evidence does not promote a parity row or establish biological
prediction superiority. Portable workflows and reproduction commands are in
`studies/semantic-stress/README.md`; frozen inputs/reports live in the local
sibling `ligare/data/molframe-research/experimental`, not in a standalone clone.
The publisher SKEMPI 2.0 supplement contains 7,085 experimental records; a pinned
CSV mirror is checked against original scientific fields. The deterministic
fourteen-complex pilot retains 631 measures of 545 residues after excluding
censored/ambiguous measurements, discordant source rows, mismatched reference
and mutant temperatures, and an explicitly contradictory experimental WT identity.
The assay-condition amendment followed preliminary analysis, whose protocol and
results remain archived. It is not external preregistration.

| Boundary | Observed evidence |
|---|---|
| Experimental residue identity | 545 author-chain/residue/insertion/WT joins; independently checked with Gemmi |
| Admissible geometry pilot | 168 configurations: fourteen structures × twelve heavy-atom vdW policies |
| Domain kernel reference | 468 residue-degree comparisons against ProLIF over 1BRS, 1GUA and 4PWX; no differences |
| Wrong identifier namespace | 371 measured residues changed or lost across eight systems |
| Baseline / uniform policy median | Equal-weight AUROC 0.7223 / 0.7197; held-out balanced accuracy 0.6755 / 0.6871 across eleven two-class systems |
| Outcome dependence on policy | Contact degree changes for 204 of 545 measured residues |
| Sequence leakage screen | 473 cross-group chain comparisons; no pair has both >=30% identity and >=80% coverage under the recorded alignment |

Seven residues have conflicting measured hotspot labels and stay ambiguous.
Three systems have a single class and retain unavailable AUROC/accuracy rather
than being silently removed from the corpus. Bootstrap summaries condition on
fitted predictions and do not establish confirmatory significance. Grouping uses
source holdout metadata/shared names; the sequence screen is not exhaustive
family validation. Experimental construct/state matching, external frozen
validation and an additional biological task remain pending. A checked generic
runner can perform the same identity safeguards; enumeration itself is not novelty.


## Python/Rust release-boundary checks (0.5.0, 2026-10-04)

The Python package remains a curated interface over native kernels, not a
one-for-one export of every low-level Rust type. The local Python suite passed
337 tests; strict Pyright reported no errors and `--verifytypes` reported 100%
type completeness. Type completeness alone is not numerical parity.

`molframe-py` tests directly compare Python and Rust centroid, distance matrix,
RMSD, TM-score and GDT on the same 1UBQ coordinates, plus internal-coordinate
seeds, Cartesian rebuilding, BAT measurement and BAT rebuilding. The numerical
array test runs in the Python CI/release job with NumPy on the embedded
interpreter's search path. Lengths retain Å; IC/BAT angles retain Rust radians,
while the established Python angle/torsion array operations return degrees.

The optional external-corpus test compared all 5,316 Ligare refined-set SDFs:
Python and Rust atom counts and every coordinate were identical. Reproduce it
with `MOLFRAME_PARITY_CORPUS` pointing to that acquired corpus, `PYO3_PYTHON`
pointing to the project interpreter, and `PYTHONPATH` containing its site-packages:
`cargo test -p molframe-py python_and_rust_read_the_same_external_ligand_corpus -- --ignored --nocapture`.
The corpus is not bundled and this check does not validate chemical truth.

The release workflow installs each built wheel into an isolated environment,
asserts that import resolves inside that environment, and runs the Python
contract suite on Linux x86-64/arm64, macOS x86-64/arm64 and Windows x86-64
before publication. This is a gate, not a claim that those remote runs have
already completed.
