# 0.3.0 evidence ledger

This page is the acceptance ledger for the 0.3.0 workbench scope. It separates
implemented code from behavior that has been exercised at the public boundary.
A capability is not marked complete because a type, binding, or handle exists.
The ledger must be updated with a reproducible command, fixture, and observed
result when a row changes.

## Status vocabulary

- **Exercised** — the consumer-visible path was run and its expected result was
  observed. The evidence column identifies the test, fixture, or UI workflow.
- **Partial** — some implementation or lower-level coverage exists, but an
  acceptance boundary, error path, or integration path remains unverified.
- **Missing** — the required behavior is not implemented or no usable evidence
  exists.
- **Blocked** — implementation is present, but an external prerequisite (for
  example unavailable hardware or a provider) prevents the specified scenario.
  A blocked row is not a pass.

The status applies to the requirement, not to the apparent maturity of its
implementation. `cargo check`, a binding smoke test, or a non-empty result is
not evidence for an end-to-end row.

## Required evidence record

For each exercised row, record:

1. the exact command or UI workflow and repository revision;
2. fixture identity, source format, viewport/DPR/device, and relevant options;
3. observed output, including expected failures and diagnostics;
4. test discovery count and process exit status where a test runner is used;
5. external limitations, unsupported capabilities, and raw artifact paths.

A skipped WebGPU backend, unavailable notebook host, provider outage, or
missing redistributable chemistry resource must be recorded as a limitation;
none converts a partial row into an exercised row. Keep implementation notes in
the owning module and keep this page limited to acceptance evidence and status.

## Measured performance against the specification targets

Release build on an Apple M5 Pro, Criterion with warm-up, revision `787a0a7` plus
the selection scans described below. Inputs are the embedded 1AON (58,870 atoms),
4HHB and smaller structures. Linear scaling to 100,000 atoms is stated as
extrapolation, not as a measurement.

| Target | Measured | Verdict |
| --- | --- | --- |
| mmCIF read to a `Structure` above 200 MB/s (program target 300 MiB/s) | `cif_read`: 231 MiB/s 1CRN, 216 MiB/s 1UBQ, 228 MiB/s 4HHB (3.20 ms), from 198–211 MiB/s | Spec target met; the 300 MiB/s program target is not. Top remaining frame: `Lexer::next_token` (about a third of samples), then the projection sink and number parsing |
| BinaryCIF container parse above 1 GB/s | 0.37–4.4 GiB/s (1CRN to 1AON) | Met for the larger inputs |
| BinaryCIF read to a `Structure` above 1 GB/s | `bcif_read/1aon`: 7.53 ms for 2.77 MiB, 369 MiB/s end to end (13.96 ms, 199 MiB/s before); 4HHB 462 MiB/s. Split: `bcif_decode_columns/1aon` 2.40 ms, `bcif_lower/1aon` 5.13 ms (11.29 ms before) | Not met. Top remaining frames: per-row symbol lookups (`symbol_of`), `decode_stage`, `ChunkBuilder::push` |
| `Document` to `Structure` for 100,000 atoms, under 20 ms | `cif_lower/100k`: 58.5 ms on 100,000 tiled 1AON atoms (69.5 ms before) | Not met |
| Time to first atom, 5 MB mmCIF | `cif_first_atom/5mb`: 12.8 µs (bounded-window batch source, first batch) | Met |
| Full facade read (`read_bytes`) of 58,870 atoms | `facade_enrich/1aon` (default perception alone): 10.97 ms, from 31.3 ms; bond perception now runs in parallel cell blocks | Reported |
| Topological selection, 100,000 atoms, under 1 ms | `chain A` 0.014 ms, `bfactor > 20` 0.31 ms on 58,870 atoms; `query_prune/element_zn_100k`: 105 ns with chunk-statistics pruning (0.97 ms before) | Met |
| SASA, 100,000 atoms, 960 points, under 2 s | `shrake_rupley_100k_960`: 122 ms on 100,000 atoms (232.5 ms before), one streaming engine with lane-parallel occlusion | Met |
| Radius query, 100,000 atoms, 5 Å, under 100 µs | `spatial_cell_list/radius_100k_5A`: 294 ns against a prebuilt index | Met |
| Cell-list build, 100,000 atoms, under 5 ms | `spatial_cell_list/build_100k`: 1.37 ms (eager `CellList::build_in`) | Met |
| RMSD, 10,000 atoms | `geom_coordinates/rmsd_10k`: 6.68 µs (1.50 Gelem/s) | Reported |
| Coordinate hand-off to NumPy without a copy | `facade_handoff/positions_slice`: 0.83 ns; the slice pointer is asserted equal across calls | Met |
| Python import under 50 ms | 1.2 ms median over five subprocess imports of a release abi3 build; `python/tests/test_import_time.py` asserts the 50 ms budget | Met |

Column predicates used to cost one hierarchy walk and a binary search per atom.
Residue- and chain-level predicates now decide once per residue and return runs,
and the thresholded `bfactor` and `occupancy` columns read each chunk directly.
On 58,870 atoms `chain A` fell from 1.05 ms to 0.014 ms and `bfactor > 20` from
0.72 ms to 0.31 ms; on 4HHB the typed and textual selection benchmarks fell from
44 µs and 93 µs to 17 µs. `bfactor > 20` keeps most atoms, so the rest of its
cost is building the selection rather than comparing values.

### Optimisations tried and reverted

Each was measured before and after on an Apple M5 Pro and reverted because the
named benchmark did not improve.
